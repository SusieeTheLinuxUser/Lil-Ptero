# AGENTS.md

Instructions for AI coding agents (and a decent map for human contributors too) working on this repo. If you're a human, read [README.md](README.md) first for setup, then skim this for conventions before opening a PR.

## What this is

An open-source Android app (Flutter) that talks directly to a Pterodactyl panel's Client API to let someone view and control their Minecraft server(s) from their phone — resource stats, power actions, and a live console. Works with any Pterodactyl host; there's no backend of ours in the middle. See [README.md](README.md) for the user-facing pitch and current feature status.

## Ground rules for this codebase

This project is deliberately minimal. Before adding a dependency or an abstraction, check whether the Flutter/Dart SDK, a native Android feature, or an already-installed package already covers it. Concretely, on this repo that has meant:

- `dart:io WebSocket.connect` directly for the console socket — no `web_socket_channel` (Android-only app, so `dart:io` is always available).
- `ChangeNotifier` / plain `StatefulWidget` state — no `provider`/`riverpod`/`bloc`.
- Manual `fromJson` constructors — no `json_serializable`/`build_runner`/`freezed`. A Dart 3 `sealed class` (`ConsoleEvent` in [lib/models.dart](lib/models.dart)) gets exhaustive-union handling for free from the language.
- Plain `Navigator.push`/`MaterialPageRoute` — no `go_router` (the flow is linear, no deep links).
- Hand-rolled `formatBytes`/`formatUptime` in [lib/format.dart](lib/format.dart) — no `intl`.

Keep following this pattern: reach for the SDK/stdlib/native feature first, and only add a package when there's a genuine gap (the only two real dependencies today are `http` and `flutter_secure_storage` — see [pubspec.yaml](pubspec.yaml) for why).

Don't add speculative abstractions, config for values that never change, or scaffolding "for later." A `ponytail:`-style comment in the code marking a deliberate corner cut (e.g. single-page server list fetch, no auto-reconnect backoff) means: that's intentional for v1, not a bug — extend it only when it's actually needed, not preemptively.

## Repo layout

```
lib/
  main.dart                   — app entry point, routes to Setup or Server List based on saved credentials
  credentials.dart            — panel URL + API key, stored via flutter_secure_storage (Android Keystore)
  api_client.dart             — PterodactylApiClient: all REST calls, throws ApiException
  console_socket.dart         — ConsoleSocket (websocket I/O) + ConsoleStateMachine (pure, unit-testable auth/token-refresh logic)
  models.dart                 — PteroServer, ServerResources, WebsocketDetails, ConsoleEvent (sealed), manual fromJson
  format.dart                 — formatBytes, formatUptime
  theme_prefs.dart            — dark-only theme, selectable accent color presets (persisted via flutter_secure_storage)
  screens/                    — Setup, Server List, Server Detail (Overview + Console tabs), Settings
  widgets/resource_gauge.dart — shared CPU/RAM/disk bar

test/                         — flutter_test only, no mocking packages; targets pure logic (models, format, console state machine)
android/                      — generated by `flutter create --platforms=android .`; don't hand-edit generated Gradle files unless you know why
assets/icon/                  — app icon source: icon.svg (legacy/full-bleed) + icon_foreground.svg (adaptive-icon safe zone), rasterized to icon.png / icon_foreground.png
```

### App icon

The launcher icon is generated, not hand-placed in `android/`. To change it: edit `assets/icon/icon.svg` and `assets/icon/icon_foreground.svg`, rasterize both to `assets/icon/icon.png` / `icon_foreground.png` (1024x1024, e.g. via `rsvg-convert`), then regenerate every density + the adaptive-icon XML with:

```bash
dart run flutter_launcher_icons
```

`icon.svg` should include the background (used as the legacy pre-Android-8 icon); `icon_foreground.svg` must be transparent-background full-bleed art — `flutter_launcher_icons` applies Android's standard ~16% safe-zone inset itself, so don't pre-pad the foreground art or it'll end up tiny.

There is no `models/`/`services/`/`providers/` subfolder split — the file count doesn't justify it. Don't introduce one preemptively.

## Build / test / run

Requires the Flutter SDK (stable channel) and an Android SDK. See [README.md](README.md) for install steps.

```bash
flutter pub get       # fetch dependencies
flutter analyze       # static analysis — must be clean
flutter test          # unit tests — must pass
flutter run           # run on a connected device/emulator
flutter build apk --debug   # sanity-check a full build
```

Known local gotcha: if your default JDK is very new (e.g. 21+), the Android Gradle Plugin's `jlink` step can fail. Fix with `flutter config --jdk-dir=/path/to/jdk-17`.

**Always run `flutter analyze` and `flutter test` before considering a change done.** Every non-trivial piece of logic (a branch, a parser, the console state machine) should leave a runnable test behind — see `test/console_state_test.dart` for the pattern (script a sequence of events through a pure state machine, assert the resulting state, no real socket).

## The Pterodactyl Client API (what this app talks to)

Base path: `{panel_url}/api/client`, header `Authorization: Bearer {api_key}`, `Accept: application/json`. The user supplies their own panel URL + a personal **Client** API key (not an Application/admin key) — see [lib/api_client.dart](lib/api_client.dart) for everything currently implemented:

- `GET /api/client` — list servers
- `GET /api/client/servers/{id}` — server details
- `GET /api/client/servers/{id}/resources` — polled for live stats
- `POST /api/client/servers/{id}/power` — `{"signal": "start"|"stop"|"restart"|"kill"}`
- `GET /api/client/servers/{id}/websocket` — returns a short-lived token + wss:// URL for the console

Console websocket protocol (see [lib/console_socket.dart](lib/console_socket.dart)): send `{"event":"auth","args":[token]}`; receive `console output` / `status` / `stats` / `token expiring` / `token expired`; send commands via `{"event":"send command","args":[cmd]}`. On `token expiring`, fetch a fresh token via REST and re-auth on the **same** open socket — no reconnect needed. `token expired` means the server will close the socket.

Not yet implemented (intentionally out of v1 scope, see roadmap below): file manager, backups, schedules, databases, subusers, server creation.

## Security norms

- Never hardcode a panel URL, API key, or any other credential in source, tests, or comments — the whole point of this app is that credentials are user-supplied at runtime and stored only in `flutter_secure_storage` (Android Keystore-backed).
- Don't `print`/`debugPrint` credentials, tokens, or full request/response bodies that might contain them.
- Don't add cleartext (HTTP) support or a custom network security config that weakens the OS default — Android already blocks plaintext traffic by default on this app's target SDK, which is correct given the app sends a bearer credential on every request.
- If you touch `credentials.dart` or `api_client.dart`, double-check nothing new gets logged or serialized somewhere it shouldn't.

## Roadmap / known scope cuts (don't "fix" these without discussion)

- Android only — no iOS build yet.
- Single-panel connection at a time — no multi-panel/multi-account support.
- Server list handles only the first page of results (`meta.pagination` from `GET /api/client` isn't followed).
- Console reconnect after a drop is manual (a button), not automatic with backoff.
- No file manager, backups, schedules, or database management.

These are deliberate v1 cuts, not oversights — check with the maintainer (or open an issue) before taking on one of these as a big PR.

## PR expectations

- Keep diffs minimal and scoped to the stated change — this project actively resists scope creep and unrequested abstraction.
- Run `flutter analyze` and `flutter test` before opening a PR; note the results in the PR description.
- If you add non-trivial logic, add or extend a test the way `test/console_state_test.dart` does.
- Explain *why*, not just *what*, in the PR description if the change isn't self-evident from the diff.
