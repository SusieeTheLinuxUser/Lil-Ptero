# AGENTS.md

Instructions for AI coding agents (and a decent map for human contributors too) working on this repo. If you're a human, read [README.md](README.md) first for setup, then skim this for conventions before opening a PR.

For the active F-Droid reviewer-response task, read [fdroid/AI_HANDOFF.md](fdroid/AI_HANDOFF.md) first; it is the compact current-state handoff and avoids rereading this entire file.

## What this is

An open-source Android app (Flutter) that talks directly to a Pterodactyl panel's Client API to let someone view and control their Minecraft server(s) from their phone — resource stats, power actions, and a live console. Works with any Pterodactyl host; there's no backend of ours in the middle. See [README.md](README.md) for the user-facing pitch and current feature status.

## Ground rules for this codebase

This project is deliberately minimal. Before adding a dependency or an abstraction, check whether the Flutter/Dart SDK, a native Android feature, or an already-installed package already covers it. Concretely, on this repo that has meant:

- `dart:io WebSocket.connect` directly for the console socket — no `web_socket_channel` (Android-only app, so `dart:io` is always available).
- `ChangeNotifier` / plain `StatefulWidget` state — no `provider`/`riverpod`/`bloc`.
- Manual `fromJson` constructors — no `json_serializable`/`build_runner`/`freezed`. A Dart 3 `sealed class` (`ConsoleEvent` in [lib/models.dart](lib/models.dart)) gets exhaustive-union handling for free from the language.
- Plain `Navigator.push`/`MaterialPageRoute` — no `go_router` (the flow is linear, no deep links).
- Hand-rolled `formatBytes`/`formatUptime` in [lib/format.dart](lib/format.dart) — no `intl`.

Keep following this pattern: reach for the SDK/stdlib/native feature first, and only add a package when there's a genuine gap. Today that's four: `http` and `flutter_secure_storage`, plus `flutter_local_notifications` and `flutter_background_service` for the background monitor (Dart has no way to post an Android notification or run a foreground service on its own). The one-off "ignore battery optimizations" Intent is a ~15-line platform channel in [MainActivity.kt](android/app/src/main/kotlin/dev/susiee/lilptero/MainActivity.kt) rather than a fifth package — prefer that trade when a plugin would exist solely to fire one Intent.

`flutter_local_notifications` requires Java core-library desugaring, which is why `isCoreLibraryDesugaringEnabled` and the `desugar_jdk_libs` dependency are in [android/app/build.gradle.kts](android/app/build.gradle.kts). Don't remove them.

Don't add speculative abstractions, config for values that never change, or scaffolding "for later." A `ponytail:`-style comment in the code marking a deliberate corner cut (e.g. single-page server list fetch, no auto-reconnect backoff) means: that's intentional for v1, not a bug — extend it only when it's actually needed, not preemptively.

```
  console_socket.dart         — ConsoleSocket (websocket I/O) + ConsoleStateMachine (pure, unit-testable auth/token-refresh logic)

  update_check.dart           — update check: F-Droid API (installed by an F-Droid client, never GitHub) or GitHub's /releases/latest 302; pure version parsing/comparison
  update_prefs.dart           — "Check for updates" toggle + once-per-24h start check + update banner

android/                      — generated by `flutter create --platforms=android .`; don't hand-edit generated Gradle files unless you know why
assets/icon/                  — app icon source: icon.svg (legacy/full-bleed) + icon_foreground.svg (adaptive-icon safe zone), rasterized to icon.png / icon_foreground.png
```

### App icon

The launcher icon is generated, not hand-placed in `android/`. To change it: edit `assets/icon/icon.svg` and `assets/icon/icon_foreground.svg`, rasterize both to `assets/icon/icon.png` / `icon_foreground.png` (1024x1024, e.g. via `rsvg-convert`), then regenerate every density + the adaptive-icon XML with:

```bash
dart run flutter_launcher_icons
```

`icon.svg` should include the background (used as the legacy pre-Android-8 icon); `icon_foreground.svg` must be transparent-background full-bleed art — `flutter_launcher_icons` applies Android's standard ~16% safe-zone inset itself, so don't pre-pad the foreground art or it'll end up tiny.

There is no `models/`/`services/`/`providers/` subfolder split — the file count doesn't justify it. Don't introduce one preemptively.

### Background server-status notifications

Opt-in (off by default) toggle in Settings starts an Android **foreground service** that polls every server's state every 30s via REST and posts a notification when one transitions to offline. It deliberately does *not* hold websockets — one `listServers()` + `getResources()` pass per tick is far less code than N sockets with token refresh in a background isolate. State is diffed against the previous tick, persisted in `flutter_secure_storage`; `shouldNotifyOffline()` is pure and unit-tested.

**Read this before touching `background_monitor.dart`.** Every one of these failed *silently* on a real device — service alive, notification posted, zero work done, no crash and nothing in logcat. They cost hours to find:

- **The `onStart` callback MUST be a public top-level function.** It was a private static method (`BackgroundMonitor._onStart`). `PluginUtilities.getCallbackHandle()` returns a perfectly valid-looking non-zero handle for one, but the background isolate can't resolve it back, so the plugin's entrypoint hits `if (onStart != null)` and does nothing at all. The plugin's docstring says "top-level or static"; in practice only top-level works. Don't move it into a class for tidiness.
- **Don't pass a custom `notificationChannelId`** unless you create that channel first — the plugin only auto-creates its own default channel when the id is left unset. Passing an uncreated id makes Android reject the foreground notification (`CannotPostForegroundServiceNotificationException`).
- **`foregroundServiceType` must be declared in our manifest.** The plugin's own manifest declares none and Android 14+ requires one (`MissingForegroundServiceTypeException`). It's merged in via `tools:node="merge"` on the plugin's `<service>`; don't redeclare the whole element, that collides with the plugin's `exported`/`stopWithTask` values. Use `specialUse`, never `dataSync` (Android 15 time limit and boot-start ban, see the 2026-11-08 notes).
- The persistent notification shows a last-checked time on purpose. It's the only cheap signal that the watcher is alive — keep it.

**Verifying on a device.** Dart `print`/`debugPrint` from the service isolate did not reach logcat on the test device, and OEM logcat noise buries everything anyway. What actually works is inspecting Android's own state over adb:

```bash
adb shell dumpsys activity services dev.susiee.lilptero   # is the FGS alive? isForeground / createTime
adb shell dumpsys notification --noredact                 # the notification's android.text + numUpdatedByApp
adb shell dumpsys deviceidle whitelist | grep lilptero    # battery-optimization exemption granted?
adb shell run-as dev.susiee.lilptero cat /data/data/dev.susiee.lilptero/shared_prefs/id.flutter.background_service.xml
```

`numUpdatedByApp=0` on the notification is the tell that the isolate never ran. The `shared_prefs` dump (debug builds only — `run-as` won't work on release) shows the stored `background_handle`, which changes whenever the callback function identity changes — useful for confirming `configure()` actually picked up your edit. Debug and release behave identically here; the bugs above are not build-mode artifacts.

**OEM power management.** The standard `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` prompt ([battery_optimization.dart](lib/battery_optimization.dart)) only covers stock Android Doze. Samsung, Xiaomi, OPPO/OnePlus, Huawei etc. each layer their own background killer on top that this prompt doesn't touch — on the OPPO test device, "Allow background activity" in the vendor battery manager was required as well. Consult [dontkillmyapp.com](https://dontkillmyapp.com) for per-vendor specifics before concluding a background bug is ours.

## Build / test / run

Requires the Flutter SDK (stable channel) and an Android SDK. See [README.md](README.md) for install steps.

```bash
flutter pub get       # fetch dependencies
flutter analyze       # static analysis — must be clean
flutter test          # unit tests — must pass
flutter run           # run on a connected device/emulator
flutter build apk --debug   # sanity-check a full build
```

Known local gotcha: if your default JDK is very new (e.g. 21+), the Android Gradle Plugin's `jlink` step can fail. Fix with `flutter config --jdk-dir=/path/to/jdk-17`.

**Always run `flutter analyze` and `flutter test` before considering a change done.** Every non-trivial piece of logic (a branch, a parser, the console state machine) should leave a runnable test behind — see `test/console_state_test.dart` for the pattern (script a sequence of events through a pure state machine, assert the resulting state, no real socket).

`.github/workflows/ci.yml` runs both on every PR and on pushes to `main`; `main` is protected and requires that check to pass. Automated tests cover pure logic, mocked HTTP, loopback WebSockets, and widget behavior; Android services, notifications, and background isolates still **must** be verified on a real device (see the adb recipes above).

### API and console reliability validation (2026-09-26)

- `api_client.dart` converts malformed JSON and invalid GET payload types into `ApiException`, rejects non-2xx responses, and accepts empty successful power responses. Keep response bodies and credentials out of error messages and logs.
- `console_socket.dart` disconnects safely on malformed frames or failed token refresh, suppresses duplicate refresh requests, and ignores late responses after disconnect/disposal. Disposal during token lookup or the WebSocket handshake must not leave an authenticated socket behind. Commands require successful authentication.
- `screens/console_tab.dart` owns the socket while connecting, waits for authentication before enabling commands, and guards Reconnect before disposing anything. Rapid repeat taps must not cancel the new attempt. Its optional API client supports widget tests and is closed when the tab is disposed.
- `screens/setup_screen.dart` checks `mounted` before displaying an asynchronous API error.
- Regression coverage: `test/api_client_test.dart`, `test/console_socket_test.dart`, and `test/console_tab_test.dart`. Use synthetic credentials, reserved example domains, and ephemeral loopback sockets only; no live panel is needed. Widget tests drain asynchronous stream cleanup with `tester.runAsync` before asserting the next UI state.
- Validated locally: `flutter test --no-pub` (49 tests), `flutter analyze --no-pub`, `flutter build apk --debug --no-pub`, and `git diff --check` passed. No dependencies or release/F-Droid configuration were changed by this work.
- Still requires real Android verification: live panel authentication/token renewal, network loss and manual reconnect, and navigation/backgrounding during connection setup. A debug APK build and loopback tests do not establish device behavior.

### Bug hunt notes (2026-11-07)

- `main()` must reach `runApp` even if a prefs `load()` throws; each is wrapped in `.catchError`.
- Backup restore vs. flutter_secure_storage (fixed 2026-11-07): its values are encrypted with a Keystore key that never leaves the phone, so a restored copy can't be decrypted. `res/xml/backup_rules.xml` (API ≤30) and `data_extraction_rules.xml` (31+, cloud + device transfer) exclude the plugin's two files, `FlutterSecureStorage.xml` and `FlutterSecureKeyStorage.xml` (names from the plugin 9.2.4 source; recheck if the plugin is upgraded or `sharedPreferencesName` is set). `allowBackup` stays on. For data already restored by an older build, `_StartupGate` catches a failed `Credentials.load()`, calls `Credentials.reset()` (`deleteAll`; works without decrypting, and the plugin makes a fresh key on its own) and shows the setup screen with a notice. Don't move that reset into `load()`: the background isolate calls it too and would wipe silently. Setup and Disconnect show an error if a storage write or delete fails. Covered by `test/credentials_restore_test.dart` (mocked plugin channel); the real restore path still needs a device check.
- Android's cleartext block does NOT reach `dart:io`: Flutter's Android embedder never sets `--disallow-insecure-connections`, so plain `http://` works and would send the bearer key unencrypted. `api_client.dart` `_send` therefore refuses any non-https panel URL (covers setup and saved URLs). Keep that check.
- The console socket sets `pingInterval` so a half-open connection closes and shows Reconnect.

### Bug hunt notes (2026-11-08)

- The monitor's foreground service type is `specialUse` (permission `FOREGROUND_SERVICE_SPECIAL_USE`), not `dataSync`. The app targets SDK 36, and Android 15 caps `dataSync` at 6 h per day (the plugin has no `onTimeout`, so the app would crash) and forbids starting it from `BOOT_COMPLETED`. The plugin passes `FOREGROUND_SERVICE_TYPE_MANIFEST`, so the manifest alone decides. Needs a device check: monitor still alive after a reboot and after 6+ h.
- POST_NOTIFICATIONS is requested only when the user turns the monitor on (`NotificationPrefs.setEnabled(true)`), not on every launch. If it's denied, the toggle stays off and Settings shows a SnackBar. Covered by `test/notification_prefs_test.dart`.
- `_pollOnce` throws when there are no saved credentials, so the persistent notification says "Check failed" rather than a misleading "Last checked".
- The console's "disconnected" banner waits for the first connect attempt (`_socket != null`), so a swipe into the tab doesn't flash it.

## The Pterodactyl Client API (what this app talks to)

Base path: `{panel_url}/api/client`, header `Authorization: Bearer {api_key}`, `Accept: application/json`. The user supplies their own panel URL + a personal **Client** API key (not an Application/admin key) — see [lib/api_client.dart](lib/api_client.dart) for everything currently implemented:

- `GET /api/client` — list servers
- `GET /api/client/servers/{id}` — server details
- `GET /api/client/servers/{id}/resources` — polled for live stats
- `POST /api/client/servers/{id}/power` — `{"signal": "start"|"stop"|"restart"|"kill"}`
- `GET /api/client/servers/{id}/websocket` — returns a short-lived token + wss:// URL for the console

Console websocket protocol (see [lib/console_socket.dart](lib/console_socket.dart)): send `{"event":"auth","args":[token]}`; receive `console output` / `status` / `stats` / `token expiring` / `token expired`; send commands via `{"event":"send command","args":[cmd]}`. On `token expiring`, fetch a fresh token via REST and re-auth on the **same** open socket — no reconnect needed. `token expired` means the server will close the socket.

Not yet implemented (intentionally out of v1 scope, see roadmap below): file manager, backups, schedules, databases, subusers, server creation.

## Security norms

- Never hardcode a panel URL, API key, or any other credential in source, tests, or comments — the whole point of this app is that credentials are user-supplied at runtime and stored only in `flutter_secure_storage` (Android Keystore-backed).
- Don't `print`/`debugPrint` credentials, tokens, or full request/response bodies that might contain them.
- Don't add cleartext (HTTP) support or a custom network security config that weakens the OS default — Android's cleartext default does not cover `dart:io`, so `api_client.dart` refuses non-https panel URLs itself; the app sends a bearer credential on every request.
- If you touch `credentials.dart` or `api_client.dart`, double-check nothing new gets logged or serialized somewhere it shouldn't.

## Releases & distribution

- **Application ID**: `dev.susiee.lilptero` — permanent, can never change once anything is published (F-Droid and every installed copy are tied to it). Don't touch `applicationId`/`namespace` in `android/app/build.gradle.kts` or move `MainActivity.kt`'s package without understanding that consequence.
- **GitHub Releases**: `.github/workflows/release.yml` builds a signed release APK and publishes it automatically when a tag matching `v*.*.*` is pushed. Release checklist (as done for v0.1.3 and v0.1.4), all in one release PR:
  - Bump `version:` in `pubspec.yaml` (`X.Y.Z+buildNumber`, build number +1) **and** `appVersion` in `lib/update_check.dart`; `test/update_check_test.dart` fails if they drift. Tests that need a "newer" version use `99.0.0`, so they survive bumps.
  - Add F-Droid changelogs `fastlane/metadata/android/en-US/changelogs/<build*10+1..3>.txt` (one per ABI versionCode, same text, under 500 chars).
  - After the PR merges, tag the merge commit annotated with the merge message (`git tag -a vX.Y.Z -m "<merge subject>" -m "<PR title>"`) and `git push origin vX.Y.Z`. CI signs and uploads the 3 split APKs; signing secrets live only in GitHub Actions, so don't build release APKs locally to ship.
  - CI's release body is only auto-generated PR titles. Afterwards, prepend a `## What's new` section (the changelog text) with `gh release edit vX.Y.Z --notes-file`.
  - Check the published APKs: `aapt2 dump badging` (versionCodes build*10+1/2/3) and `apksigner verify --print-certs` (SHA-256 `940bcf55…56a6`, the key pinned in the F-Droid recipe). v0.1.4 = 51/52/53, tag annotated (v0.1.2/v0.1.3 are lightweight; either triggers the workflow).
  - CodeRabbit allows 10 reviews per hour; when it says "Review limit reached", a fix commit may get no re-review for a while.
  - The F-Droid recipe (`fdroid/dev.susiee.lilptero.yml`) is not updated by this; syncing the MR to a new version is a separate task (new commit SHA, versionCodes, and reproducibility re-check).
- **Release signing**: `android/key.properties` + `android/keystore/release-key.jks` are gitignored and never committed — the Gradle config in `android/app/build.gradle.kts` falls back to debug signing when they're absent, so a fresh checkout still builds fine, just unsigned-for-release. CI gets the real key from GitHub Actions secrets (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`), written to those same files at build time.
- **`dependenciesInfo { includeInApk = false }`** in `android/app/build.gradle.kts` — don't remove this. Without it, AGP embeds a Play Console dependency-metadata block in the signing block that F-Droid's build scanner rejects outright (this is what broke v0.1.0's submission). Harmless to keep even if we never touch F-Droid again.

## Roadmap / known scope cuts (don't "fix" these without discussion)

- Android only — no iOS build yet.
- Single-panel connection at a time — no multi-panel/multi-account support.
- Server list handles only the first page of results (`meta.pagination` from `GET /api/client` isn't followed).
- Console reconnect after a drop is manual (a button), not automatic with backoff.
- No file manager, backups, schedules, or database management.

These are deliberate v1 cuts, not oversights — check with the maintainer (or open an issue) before taking on one of these as a big PR.

## PR expectations

- Keep diffs minimal and scoped to the stated change — this project actively resists scope creep and unrequested abstraction.
- Run `flutter analyze` and `flutter test` before opening a PR; note the results in the PR description.
- If you add non-trivial logic, add or extend a test the way `test/console_state_test.dart` does.
- Explain *why*, not just *what*, in the PR description if the change isn't self-evident from the diff.
